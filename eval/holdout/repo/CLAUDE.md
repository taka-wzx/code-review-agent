# tracker 项目约定

乒乓球轨迹追踪。双目相机 125fps，坐标系：桌面为 z=0，+y 从机器人侧指向对
面。内部所有位置单位一律**毫米**，速度对外报告用 km/h。

## 1. 代码风格

- Python 3.10；函数small而单一职责；公共函数写 docstring。
- 文件 IO 一律用 `with`。

## 5. 已知教训（新代码必须遵守）

### 5.1 弹跳 overshoot/undershoot 必须按飞行方向投影判定

overshoot 的定义是"预测落点比实际落点**沿飞行方向**更远"，不是"y 坐标更大"。
飞行方向由快照时刻的 `vy_at_snap` 给出：球可能朝 +y 飞也可能朝 -y 飞
（对打数据里 `vy_at_snap < 0` 约占一半）。

判定必须先投影：`along = bounce_dy_mm * sign(vy_at_snap)`，`along > 0`
才是 overshoot。直接拿 `bounce_dy_mm > 0` 判定，在 vy_at_snap < 0 的球上
结论正好相反——2026-05 的标定分析里真实踩过这个坑，浪费了两天。
**x 轴同理**：`bounce_dx_mm` 必须用 `sign(vx_at_snap)` 投影。

### 5.2 单位换算

位置是 mm、帧间隔是秒时，`dist / dt` 得到的是 **mm/s**；换 m/s 要再除
1000。历史上出过一次速度大三个数量级的事故，换算处必须写明中间单位。

### 5.3 一切步长门必须感知 dt

125fps 采集**漏帧很常见**（相邻已接受点的间隔经常是 2-3 个帧周期）。任何
"两点间距离超过 X 就拒绝"的门都会误杀漏帧后的合法快球。门必须除以 dt 按
速度判（mm/s 或 m/s），不能用绝对距离。2026-06 真实教训：把 300mm 绝对
门改成 step/dt > 10 m/s 后，好球通过率 20% → 50%。

### 5.4 COR 标定只用 raw 三角化速度

弹跳恢复系数（COR）标定一律用撞击帧的 **raw 三角化 vz**，不用 UKF 平滑
值：平滑会把撞击帧速度往撞击前后的均值拉（撞击是速度突变点，平滑器在突
变处必然滞后），得到的 COR 系统性偏高。2026-05 标定脚本真实教训。

## 6. 显示与日志约定

- 预测轨迹画红色 `(0, 0, 255)`，观测轨迹画橙色；HUD 不超过 6 行。
- 会话日志一律 JSONL（每行一个 JSON 对象），文件名带日期后缀。
- 调试打印用 `dbg()` 帮助函数，禁止裸 `print`（发布版要能一键静音）。
