# 产品简报：GitHub PR Review Agent

## 一句话定位

面向中小型 Python 团队的 GitHub PR Review Agent：系统自动分析 PR，默认处于 shadow
模式；只有经有权限的仓库维护者批准的 Finding 才能发布到 GitHub，并通过开发者的
accept/reject 反馈衡量噪声、人工复核时间、可靠性和成本。

这是产品方向合同，不是现状完成声明。当前仓库已有 Review 引擎、GitHub Webhook、异步任务、
SQLite 幂等状态和 canonical trace；远程身份、审批产品面、反馈采集、指标聚合和生产部署仍未
实现。现状与目标边界见 [`production-architecture.md`](production-architecture.md)。

## 要解决的问题

中小型 Python 团队通常没有专职的代码质量平台团队。PR 数量增加时，Reviewer 的时间被重复的
上下文查找和低价值意见消耗；而直接把 LLM 输出自动贴到 PR，又会因为误报、权限不清和不可追责
迅速透支信任。

产品选择的不是“自动替代 Reviewer”，而是一个受控决策链：

- Agent 承担候选问题发现、证据查找和初步过滤；
- 维护者保留发布权，shadow 默认值保证未配置仓库不会自动对外发言；
- 开发者对已发布 Finding 给出 accept/reject 反馈；
- 团队按仓库查看可计算的质量、时间、可靠性和成本指标，再决定是否扩大启用范围。

预期价值必须通过 [`business-metrics.md`](business-metrics.md) 的真实事件证明。在没有基线或
对照数据前，只能说“产品旨在减少噪声和人工时间”，不能说“已经节省了多少时间”或“已经提升
了多少质量”。

## 主要用户与权限

| 用户 | 核心任务 | 可以做 | 不可以默认做 |
| --- | --- | --- | --- |
| 组织管理员 | 决定组织是否试点以及哪些仓库可接入 | 注册仓库；配置身份提供方、成本/SLO 上限；把仓库从 shadow 切到 guarded publish；查看组织聚合指标 | 不能替代仓库维护者批准某条 Finding；不能读取用户个人记忆，因为产品不建立此类记忆 |
| 仓库维护者 | 对本仓库 Finding 承担发布责任 | 审阅证据；批准或拒绝 Finding；管理仓库规则；暂停发布；查看仓库级反馈 | 未持有当前权限或审批绑定已过期时不能发布；不能用一次笼统批准覆盖未来 Finding |
| Reviewer | 使用 Agent 结果辅助人工审查 | 在 shadow/审批界面查看 Finding、证据与状态；标记重复或低价值；提供复核意见 | 除非同时具备维护者角色，否则不能批准发布或修改仓库发布规则 |
| 普通开发者 | 接收与处理自己 PR 上的已发布 Finding | 查看 Finding 证据；明确 accept 或 reject，并可选择结构化原因 | 不能改变审批准入、全仓规则或他人的权限；反馈不形成个人画像或个人记忆 |

身份和权限是目标产品要求，当前静态 Bearer 服务并未实现这套 RBAC。任何远程发布能力都必须在
身份、权限和一次性审批绑定实现并独立评审后才能启用。

## 产品模式

### Shadow（默认）

- Webhook 可以触发分析并生成 Finding；
- Finding 仅在受控内部界面/接口中可见；
- 即使维护者完成内部判定，也不调用 GitHub 发布接口；
- 用于验证质量、人工复核负担、可靠性和成本，不制造 PR 噪声。

### Guarded publish（显式启用）

- 组织管理员对具体仓库显式启用；
- 每批发布绑定仓库、PR、head SHA、Finding 集合、维护者身份、审批时间和一次性 nonce；
- 发布前再次校验权限、head SHA、Finding 内容哈希和审批未被消费；
- 校验失败必须 fail closed，不得“先发后补审计”；
- 开发者反馈只绑定已发布的 Finding 版本。

不存在“自动发布”模式。未来若要增加，必须是新的产品/安全阶段，而不是配置项默认值调整。

## 完整业务闭环

```text
PR Webhook
→ 验签、仓库白名单与幂等检查
→ 异步 Review
→ 生成带证据和稳定身份的 Finding
→ Maintainer 审核
→ shadow 留存，或在 guarded publish 中批准后发布；拒绝则不发布
→ 开发者对已发布 Finding accept/reject
→ 按仓库和时间窗聚合质量、时间、可靠性与成本指标
→ 经样本门槛和维护者确认后更新仓库规则/反馈记忆版本
→ 后续 Review 读取已批准的仓库级上下文
```

闭环中的反馈记忆是**仓库级、可版本化、可回滚的聚合规则**，例如某类重复 Finding 的抑制规则
或仓库特有约定。它不是用户个人记忆，不按个人建立画像，也不能因单次 reject 自动改写 Finder/
Verifier prompt。规则更新必须保留来源窗口、样本量、批准者和前后版本。

## 产品成功条件

产品是否成功不看“生成了多少 Finding”，而看同一个指标面板能否回答：

1. 开发者认为已发布 Finding 中有多少可行动，拒绝原因是什么；
2. 维护者每个 PR 花了多少主动复核时间，是否比明确的人工基线更低；
3. Agent 是否稳定完成，p50/p95 时延、降级和错误是否在团队可接受范围；
4. 每个 PR 和每个 accepted Finding 的完整成本是多少；
5. 重复 webhook 是否真的没有新增任务，是否发生过任何未授权发布。

指标定义不等于已有数据。Phase 9A 不设虚构目标值；试点前应由产品与仓库负责人基于团队基线
另行冻结阈值。

## 产品范围

- **Review 是唯一产品主线**：围绕 PR、Finding、维护者审批、发布、反馈和度量形成闭环。
- **Repair 是后续高风险增强**：它涉及写文件、执行测试和创建提交；已有本地审批绑定原型与
  pilot 证据，但不接入当前发布闭环，不把 pilot 完成率当产品收益。
- **Verifier Training 是研发附录**：用于探索离线过滤器训练。Phase 8 的 synthetic 流水线
  只证明 artifact/协议闭环，真实真人标签和模型质量结论尚未完成。
- **不做聊天机器人**：交互围绕 PR、Finding、审批和反馈，不提供通用聊天入口。
- **不做用户个人记忆**：只保留最小身份审计和仓库级聚合规则。
- **不以多 Agent 为卖点**：只有在独立失败域、可测收益或权限隔离要求成立时才增加组件；
  Agent 数量本身不是产品价值。

## 事实边界

截至 2026-07-22 的可核验状态：

- `origin/master` 为 `acc0dcce077113dcbbde2478abd53cbb09a4ef2e`；对应 GitHub Actions
  run `29894645345` 的 7 个 job 全部成功；
- 本机 Python 3.13.12 运行 `scripts/verify.py`（未带 `--eval-assets`）通过 646 个测试，
  6 个环境跳过，分支覆盖率 86%，mypy 检查 26 个源文件；该验证不调用外部模型；
- Week 7.5 的真实证据只有一个私有 draft PR 的一次有界 Webhook 链路，且初次投递曾在
  GitHub 侧触发 10 秒超时；
- Week 4 的 30-PR reporting 仍是预注册计划，没有真实最终质量数字；
- Phase 8D 已有 137 条真实来源 Finder 候选和冻结真人盲标包，但没有真人标签；现有训练和
  双标/仲裁闭环是 synthetic，不允许模型质量或业务收益结论；
- 没有生产用户、生产部署、远程 OAuth/RBAC、维护者审批服务、开发者反馈数据或生产 KPI
  基线。

因此历史离线 precision/recall、fake-clock 安全结果、单次 live latency 和 synthetic 训练指标
只能作为工程证据，不能填入产品 KPI 看板或转写为“减少审查噪声/节省人工时间”的真实收益。
